# UGA 아키텍처와 설계 결정

UGA는 개인의 대학 활동을 기록하는 데서 출발하지만, 핵심은 각 활동이 다음
활동과 어떤 관계를 맺는지 보여 주는 데 있다. 화면 기능이 늘어나도 데이터 접근,
비즈니스 규칙, UI 코드가 한 파일에 얽히지 않도록 아래 계층을 분리했다.

```text
사용자
  ↓
View (CustomTkinter 화면, 입력 검증과 이벤트 전달)
  ↓
Service (성장 연결 검증, 목표 진행률 계산, 백업 등 도메인 규칙)
  ↓
Repository (CRUD와 조회 쿼리)
  ↓
Model (SQLAlchemy ORM 모델)
  ↓
SQLite
```

분석, 타임라인, AI, 파일 내보내기처럼 성격이 다른 기능은 위 흐름에 직접
섞지 않고 별도 모듈로 둔다. 이 모듈들도 데이터를 바꿔야 할 때는 Service와
Repository를 거쳐 일관된 규칙을 지킨다.

## 핵심 도메인: Activity와 GrowthLink

`Activity`는 박람회, 프로젝트, 공모전, 세미나 같은 개별 경험을 담는 중심
엔티티다. `Goal`, `Tag`, `Category`, `Schedule`, `Attachment`, `Reflection`은
Activity와 연결된다.

`GrowthLink`는 “A 활동이 B 활동으로 이어졌다”를 표현하는 자기참조 관계다.
단순히 활동을 시간순으로 정렬하는 것과 달리, 사용자가 선택과 배움의 인과를
남길 수 있다. 서비스 계층에서 자기 자신을 향하는 연결을 막아 데이터가
의미 없는 그래프로 변하는 것을 방지한다.

## 주요 설계 결정

| 결정 | 이유 | 결과 |
|---|---|---|
| View / Service / Repository 분리 | UI 변경과 DB 쿼리 변경이 서로 영향을 덜 주도록 하기 위해 | 화면 코드가 SQL과 도메인 규칙을 직접 알 필요가 없음 |
| SQLite + SQLAlchemy | 개인용 데스크톱 앱에서 설치 부담을 낮추면서 모델 중심 개발을 하기 위해 | 별도 서버 없이 실행하고, 이후 DB 교체 여지도 확보 |
| AI 호출을 `ai/ai_client.py`로 집중 | API 키, 오류 처리, 모델 호출 형식이 여러 화면에 중복되지 않도록 하기 위해 | AI 기능이 없거나 실패해도 나머지 앱은 동작 |
| 테스트용 임시 SQLite DB | 실제 사용자의 기록을 테스트가 변경하지 않도록 하기 위해 | 테스트가 독립적으로 실행되고 반복 가능 |
| 자동 백업과 복원 후 재연결 | 개인 기록의 손실 위험을 낮추기 위해 | 복원 이후에도 새 세션이 복원된 DB를 사용 |

## 테스트 전략

테스트는 UI를 직접 클릭하는 방식보다 변경 위험이 높은 비즈니스 로직에 우선
집중한다. 각 테스트는 `tests/conftest.py` fixture를 통해 새 SQLite 파일과
세션을 받는다. 따라서 목표 진행률, GrowthLink 검증, 백업/복원, AI 응답 파싱을
실행해도 실제 `database/uga.db`에는 영향을 주지 않는다.

GitHub Actions는 `main` 브랜치 푸시와 Pull Request에서 Python 3.11, 3.12
환경으로 `pytest`를 실행한다. 이로써 로컬에서는 우연히 통과한 변경이 다른
환경에서 깨지는 일을 조기에 발견한다.

## 다음 개선 후보

1. 예제 데이터 세트를 제공해 신규 사용자가 모든 화면을 즉시 둘러볼 수 있게 한다.
2. GrowthLink를 그래프 형태로 탐색하고 고립된 활동을 찾는 기능을 만든다.
3. AI 응답의 스키마 검증과 재시도 정책을 강화한다.
4. 배포 파일의 버전과 변경 내역을 GitHub Releases로 관리한다.

모델링한 데스크톱 앱입니다. UI·도메인 규칙·DB 접근을 계층으로 분리하고,
실사용 DB와 분리된 임시 SQLite 테스트 및 CI로 변경의 안정성을 관리했습니다.”
